# 研究方向 001：平铺事实与版本链如何影响不同规模模型使用长期记忆

状态：方向记录 v0.2

结论状态：`NOT_PROVEN`

更新日期：2026-09-11

## 摘要

长期记忆系统即使把正确证据交给模型，仍可能失败：模型会采用旧值、遗漏必填参数，或改写本应逐字符保真的 ID、URL 和地址。

本文提出一个窄问题：**当事实记录完全相同时，把记录平铺展示，或按“实体—属性”组织为时间版本链，这两个完整序列化方案会怎样影响同一模型家族不同规模模型的工具参数绑定？**

首轮只比较两种确定性表示，只使用包含更新或冲突事实的任务，并用 Oracle Evidence 排除检索召回的影响。实验开始前先审计公开数据能否支持信息等价的转换；如果不能，停止实验并公开失败原因。

本文是实验前的方向协议，不是已经冻结的预注册，也不声称版本链已经更好。数据审计完成后才生成 v1.0 预注册。

## 1. 为什么研究这个问题

一个长期记忆系统至少包含写入、组织、检索和使用四层。端到端分数下降时，无法直接知道是哪一层导致。

[LongMemEval](https://proceedings.iclr.cc/paper_files/paper/2025/file/d813d324dbf0598bbdc9c8e79740ed01-Paper-Conference.pdf) 将长期记忆拆为 indexing、retrieval 和 reading。[Mem2ActBench](https://aclanthology.org/2026.acl-long.370.pdf) 的实验进一步显示：更大的模型能部分补偿较弱的记忆组织；强记忆系统的失败则更多表现为证据已经取回但没有被正确使用。

这留下了一个可单独检验的架构问题：同一批已召回事实采用两种不同的序列化方案，是否会改变模型采用当前值和绑定工具参数的能力？

## 2. 研究问题与边界

主问题：

> 在 Mem2ActBench 中含更新或冲突事实的任务上，当事实字段、事实条目、工具 schema、提示词和输出评分完全相同时，平铺事实与实体—属性版本链对 Qwen2.5-Instruct 7B、32B、72B 的参数绑定结果有何影响？

首轮纳入：

- 已给定正确事实的工具参数生成；
- 同一模型家族的 7B、32B、72B 三个规模；
- 事实更新、撤回或冲突场景；
- 确定性转换和确定性评分。

首轮不研究检索、记忆写入、摘要生成、知识图谱、工具选择和完整 Agent Loop。它们会同时改变其他层，无法回答当前问题。

本文中的模型变量只称为“模型规模”。规模不是能力的完整定义，结果不能外推为通用能力等级。

## 3. 启动门槛：数据可构造性审计

先对公开数据的全部 schema 做机器检查，再用固定随机种子 `20260911` 抽取 50 题人工核对。样本按更新、撤回、显式冲突和复杂字符串多标签分层；各层至少 10 题，不足 10 题则检查该层全部样本。“复杂字符串”指 ID、URL、地址或长度至少 32 个 Unicode 码点的字符串。每题必须能够从公开数据确定性获得：

- 稳定的事实或来源记录 ID；
- 实体和属性；
- 未改写的原始值，以及数据存在时的操作类型、有效区间或状态；
- 时间戳或可验证的先后顺序；
- 来源 turn 或 provenance；
- 目标工具 schema 与 gold arguments。

审计还要证明两种输入可由同一组记录生成，不依赖额外 LLM 抽取、人工补标或仅对版本链可见的 oracle 标签。

正式全集还要逐题运行同一机器检查并冻结资格清单。缺少非目标字段的题目可按预先声明的规则判为不合格；若公开数据整体缺少表达目标语义所必需的字段，或合格样本不足以达到 v1.0 预注册所设的统计精度，研究状态改为 `BLOCKED`。转换异常属于实现错误，修复后重跑，不能当作样本不合格。审计会发布字段覆盖率、排除原因和反例。

## 4. 唯一实验变量

两种表示包含相同的事实记录和相同字段。核心字段为 `entity`、`attribute`、`value`、`event_time`、`source_id`；若任务语义需要且公开数据可恢复，还必须在两边等价加入 `operation`、`valid_from`、`valid_to` 或 `status`。无法无损表达更新、撤回或冲突解析规则的题目不得进入实验。

### F0：平铺事实

```json
[
  {"entity":"user","attribute":"delivery_address","value":"A","event_time":"t1","source_id":"s1"},
  {"entity":"user","attribute":"delivery_address","value":"B","event_time":"t2","source_id":"s2"}
]
```

记录按 `event_time`、`source_id` 全局排序。

### F1：实体—属性版本链

```json
[
  {
    "entity":"user",
    "attribute":"delivery_address",
    "versions":[
      {"value":"A","event_time":"t1","source_id":"s1"},
      {"value":"B","event_time":"t2","source_id":"s2"}
    ]
  }
]
```

记录先按 `entity`、`attribute` 分组，组内再按 `event_time`、`source_id` 排序。

F1 的层级结构由 F0 已有字段确定性派生，不增加“当前值”“已失效”等答案提示。两种表示的记录与字段值必须逐项对齐。由于 F0/F1 同时改变邻接关系、JSON 层级、重复键名、token 长度和绝对位置，本实验只估计**两个完整序列化方案的总效应**，不把结果单独归因于分组、层级或长度。若总效应存在，机制拆分属于后续消融实验。token 长度作为表示的派生属性报告。

原始对话、原子摘要和只保留最新值的状态快照不进入主实验，因为它们保留的信息不同，比较结果无法归因于组织形式。

## 5. 输入预算与样本资格

先根据审计样本统计两种完整表示的 token 长度，再冻结上下文预算。正式实验只纳入 F0、F1 都能完整容纳全部 gold facts、任务描述、工具 schema 和固定提示词的题目。

任何表示都不得截断 gold facts。若某题超限，两种表示都从主分析中排除，并单独报告排除数量、类型和长度分布。这样避免“平铺表示更长，所以丢失更多证据”成为隐藏变量。

## 6. 预注册假设

- **H1（主要）**：在 7B 模型上，F1 相对 F0 提高 Argument Exact Match。
- **H2（次要）**：F1 与 F0 的差值在 Qwen2.5-Instruct 7B、32B、72B 三个 checkpoint 间递减。这是指定 checkpoint 间的描述性差异，不作参数规模的因果解释。
- **H3（保真边界）**：F1 不应降低复杂值的逐字符准确率，因为两种表示保留相同的原始 `value`。

H1 的唯一主要终点是 Argument Exact Match。stale-value rate、H2 和 H3 都是次要诊断。查看正式测试结果后新增的解释必须标为 post-hoc。

## 7. 实验协议

1. 固定数据集版本、文件哈希、合格样本和转换器版本。
2. 固定 Oracle Evidence：目标参数相关属性的完整事实演化链，包括旧值、冲突值和最终有效值，不加入无关属性；F0/F1 使用完全相同的记录集合。
3. 用上游仓库固定 commit、固定样本和原始评分器复现其 Oracle 流程；v1.0 预注册记录期望值和容许的数值误差，超出误差则停止正式实验。
4. 从同一事实记录分别生成 F0、F1，并自动验证记录集合与字段值等价。
5. 为每题固定目标工具，只要求模型输出 arguments JSON。
6. 三个模型使用同一提示词、工具 schema、最大输出长度、服务配置和确定性解码。
7. 保存输入、原始输出、解析结果、token 用量、延迟和终止状态。
8. 正式运行前，用不进入确认性分析的固定 50 题各重复三次，只检查服务与解析稳定性。正式主分析每题、每条件运行一次，不聚合多次输出。

F0/F1 组成不可拆分的题目对。任一侧发生传输错误时，整对最多重跑一次并保留所有状态；仍失败则整对排除并计入基础设施失败率。失败率超过合格样本的 1% 时整批无效。模型返回不可解析或不符合 schema 的输出属于任务失败，不能重试或从指标中删除。

## 8. 可执行评分规则

主要指标是逐题 **Argument Exact Match**：模型输出本身必须是单个 JSON 对象，且规范化后与 gold arguments 完全一致。不从 Markdown code fence、解释文字或多个片段中抽取 JSON。

规范化规则在实验前冻结：

- 顶层非对象、重复对象键、额外字段和 schema 校验失败均判错；
- 对象键顺序不计；数组默认顺序敏感，只有冻结的评分配置明确列出的集合型路径按无序多重集比较；
- 字符串仅做 Unicode NFC 规范化，之后逐码点比较；ID、URL、地址和自由文本不做语义改写；
- 数字、布尔值按 schema 类型比较，不把字符串 `"1"` 等同于数字 `1`；
- 缺失字段与 `null` 不等价，除非 schema 明确声明；
- 评分器不应用 JSON Schema 的 `default` 注解，也不补全任何缺失值；
- 嵌套对象递归应用同一规则。

次要指标：

- **Slot micro-F1**：按规范化后的叶子字段路径和值，在全部合格题上累计 TP、FP、FN；数组元素使用索引路径，集合型路径使用值及出现次数；
- **Stale-value rate**：分母为可从公开状态转换规则唯一判断当前有效值、且至少含一个不同旧值的目标字段；分子为模型输出命中该字段旧值的次数；
- **Lossless value accuracy**：分母为 gold 中的复杂字符串字段；分子为 Unicode NFC 后逐码点相等的字段；
- **Hallucinated optional rate**：分母为 gold 未要求的可选字段；分子为模型额外输出的字段。评分器不推断默认值。

这里不使用 LLM Judge。错误分类器只处理可由 gold、版本链和 schema 确定的类别。

## 9. 统计方法与判定

所有比较均按题配对。H1 使用 7B 上 F1 与 F0 的 Exact Match 差值作为主要效应，报告按任务/历史簇重采样的 10,000 次 paired bootstrap 95% 置信区间，并以 McNemar 检验作为离散结果核对。

32B、72B 和错误类型分析均为次要结果。模型规模与表示的交互用配对差值及置信区间描述，不把三个规模分别包装成三个主要检验。

数据审计后，根据合格样本数、基线正确率和实际架构切换成本，在查看正式结果前冻结最小实际效应 `δ`、H3 的非劣效界值、目标功效和 H2 的趋势对比，并发布 v1.0 预注册。在此之前不预设“提升 5 个百分点”一类无依据的成功线。若样本量达不到预注册精度则不运行确认性实验，只发布 `NOT_PROVEN`。判定规则为：

- H1 差值置信区间下界大于 0，记为有益；上界小于 0，记为有害；
- 整个置信区间落在预注册的 `[-δ, δ]` 内，记为实际等价；
- 其余情况记为证据不足。

证据不足不会被写成“没有影响”。

## 10. 需要公开的产物

- 数据来源、许可证、版本和 SHA-256；
- 审计样本、字段覆盖率和无法转换的反例；
- F0/F1 转换器与逐题等价性检查；
- 冻结的提示词、模型标识、推理配置和评分器；
- 每题运行 manifest：sample ID、representation、model、input hash、raw output、parsed output、score、token、latency、terminal status；
- 配对统计、排除样本和失败样本；
- 一条命令可运行的最小复现实验。

正式报告必须同时发布 null result、反例和外推边界。仓库 Stars 不属于实验成功条件。

## 11. 停止条件

本阶段在以下任一情形结束：

1. 数据审计失败，发布 `BLOCKED` 结论与证据；
2. 上游 Oracle 流程无法在固定样本上复现，发布差异记录；
3. 两种表示、三个规模和预注册指标完成，所有终止状态可审计；
4. 结果精度不足以区分有意义的效应，发布 `NOT_PROVEN` 结论。

检索实验只有在本阶段结束后才另立研究问题。它不能被追加进当前实验来挽救不显著结果。
